# Production email verification repair — 21 October 2026

## Confirmed cause and scope

A real production confirmation email contained a 61-character `TokenHash`: `pkce_` followed by 56 hexadecimal characters. The old `readEmailConfirmation` accepted hexadecimal characters only, rejected this valid Supabase token before any verification request, and displayed "This link is invalid or has already been opened". This was a client parsing failure, not evidence that the email scanner had consumed that particular token. Supabase's [mail implementation](https://github.com/supabase/auth/blob/master/internal/api/mail.go) prefixes PKCE tokens; preserve the whole value.

The repair accepts prefixed/unprefixed hashes, retains explicit confirmation, scrubs URL credentials, handles a resent email opening in the same mobile document, and resumes account setup without reusing a consumed token. Stored resume state is tab-only, bounded to one hour, and matched to the current session's user before verification is skipped. A verification response without a session cannot use an unrelated existing session. Secure email change can require confirmation from both addresses and may return no session; its first confirmation now explains the remaining step. Profile persistence errors are returned to the client for retry instead of silently treating setup as complete.

Google sign-in, password login, verification policy, accounts, and workspace ownership are preserved. No database migration is required. `ensureAuthWorkspace` intentionally provisions the profile only; workspace creation remains the explicit brand submission from `/projects`, through the existing idempotent, authenticated workspace service. Do not introduce a placeholder workspace trigger.

## Exact final Supabase templates

Use the complete HTML files alongside this document as the final Dashboard bodies. They preserve Mellox branding. Both the primary button and copy/paste fallback must use the href below; `&amp;` is the HTML entity and the delivered link must contain a normal `&`.

| Confirm signup              | [confirmation.html](./confirmation.html)         | Confirm your Mellox AI email        | `https://mellox.ai/auth/confirm#token_hash={{ .TokenHash }}&amp;type=email`        |

| Magic link                  | [magic-link.html](./magic-link.html)             | Your Mellox AI sign-in link         | `https://mellox.ai/auth/confirm#token_hash={{ .TokenHash }}&amp;type=magiclink`    |
| Change email address        | [email-change.html](./email-change.html)         | Confirm your Mellox AI email change | `https://mellox.ai/auth/confirm#token_hash={{ .TokenHash }}&amp;type=email_change` |
| Reauthentication            | [reauthentication.html](./reauthentication.html) | Your Mellox AI verification code    | Show `{{ .Token }}` as a code; no verification URL                                 |

If the saved Dashboard bodies already match these files, no HTML change is needed for this parser repair. One received confirmation email was checked and used the correct fragment URL; the other five saved Dashboard bodies were not inspected. Repository files do not prove live Dashboard configuration.

Do not replace these hrefs with `{{ .ConfirmationURL }}` or a direct Supabase `/auth/v1/verify` link: scanners could consume those before the user confirms. Do not strip `pkce_`, substitute `{{ .Token }}` into `token_hash`, nest the hash inside `redirect_to`, or double-encode it. Reauthentication is code-based and must stay so. Standard prefetchers and page loads cannot redeem this flow; a scanner that actively submits confirmation actions is outside this guarantee.
